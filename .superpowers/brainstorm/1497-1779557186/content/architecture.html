Generates session tokens (HMAC-SHA256). Pre-computes scoop trajectory — a time-stamped sequence of (x,y) positions. Server holds the expected gaze answers; client can't fake them.

Replays signed event log. Checks: HMAC signature chain intact, gaze events match expected scoop positions at each timestamp, variance flags absent, duration internally consistent. Flags anomalies.

The Hard Problem: How does the server trust the client?
Problem
All detection runs on-device. Nothing stops a modified client from posting duration=61 directly to the submit endpoint and claiming ₹150 every day.
Solution: Server-issued scoop path
The scoop trajectory is generated server-side at session start and never shared in full with the client — only the current position is revealed frame by frame via the signed token. A cheating client doesn't know where the scoop will move next, so it can't pre-fabricate matching gaze events.
trajectory = [
  {t:15.2, x:0.82, y:0.31},
  {t:33.7, x:0.14, y:0.78},
  ...
] // server-held, never sent in full
Solution: HMAC event chain
Each event the client logs is HMAC-signed with a per-session server-issued key. The server replays the event chain and verifies every signature. Inserting, removing, or modifying any event breaks the chain — server rejects the session.
event = {
  type: "gaze_match",
  t: 15.3, x: 0.80, y: 0.29,
  hmac: sha256(prev_hash + payload + key)
}
Privacy: No video frames, no face images, no biometric data ever leave the device. The server receives only landmark-derived events (numbers, not faces). Compliant with India's DPDP Act 2023 — facial landmark coordinates are not classified as biometric data under the act when used transiently and not stored. Session event logs are deleted after 30 days.
